# 主口令与用户配合方式（AI 怎么取得、怎么不残留）

> 本篇不讲"怎么设一个强密码"，也**不要求用户更换现有密码**。它只规定一件事：**开发/AI 需要本地主口令来解密时，通过什么合规方式取得、用在哪、用后如何不留痕。**
> 配套：开发凭证从哪取见 [credential-storage.md](credential-storage.md)，具体取密 SOP 见 [ai-agent-credentials.md](ai-agent-credentials.md)。本文一律用 `<主口令>` 占位，不写任何真实口令。

## 一、定位：主口令是用户的，不是技能管理对象

- 用户在各网站/系统用什么密码、强度如何，是用户自己的选择；**本技能不收集、不记录、不评判、不改造**，也不主动给用户安装个人密码管理器或推动 passkey。
- 在**开发/自动化范围**内，存在唯一一把"本地主口令" `<主口令>`：它是 `.enc` 凭证库、SSH 私钥 passphrase、钥匙串等本地保管物的解锁口令，由用户本人掌握。
- AI（agent）**不持久持有**这把口令：需要时当次取得、当次用于解密、用后即从内存/变量清除，不形成任何持久副本。

> 风险知情（仅记录，不催促）：主口令同时用于多处时，单点影响面更大；这是用户在"个人单机、便利性优先"下的知情选择。技能的补偿手段是"主口令绝不外泄、所有衍生凭证加密落盘、泄漏可快速轮换"。若用户**哪天主动**想加强，再参考第七节。

## 二、主口令在开发流程里只做什么

| 用途 | 说明 | 主口令是否出现到对外物 |
|---|---|---|
| 解密 `.enc` 凭证（PAT/API key/项目密码） | 经 `secrets` 命令，解出的是**目标凭证**，主口令只用于派生密钥 | 否，仅进程内 |
| 解锁/加载 SSH 私钥到 ssh-agent | 私钥 passphrase 一次性交 agent，之后复用连接免输 | 否，交给系统 agent |
| 解锁 macOS 钥匙串 | 由系统/生物识别处理 | 否 |
| `sudo` | 优先让用户在终端亲自输入；自动化才解密 `sudo.enc` | 否 |

关键认知：**正常情况下，外部工具（GitHub、API、远程服务）永远看不到 `<主口令>`，它们看到的是解密出来的、各不相同的目标 token/key。** 这就是"直接或间接都拿不到主口令明文"的含义。

## 三、AI 取得主口令的唯一合规方式

按优先级：

1. **环境变量 `ENC_PASS`（兼容旧名 `ENCRYPT_PASS`）**：当次会话/命令注入，命令结束即随进程消失。
2. **交互安全输入**：没有环境变量时，**明确向用户询问**，由用户口述或在交互输入框键入（`read -s` 不回显）。用户已说明：他只配合提供这一把主口令，方式限于口述或交互输入。
3. **本机 `master.pass`（非交互，见第五节）**：仅在用户同意的无人值守场景。

取得与使用纪律：

- 用**变量/管道**承接并直接喂给解密命令，**不要 `echo`/`print` 出来、不要贴回对话、不要写进日志**；
- 一条命令内"取—用—弃"，结束 `unset`；需要展示凭证时只显示掩码（`ghp_xxxx…后4位`）；
- **不猜测、不写死默认值、不在多个文件里复制**；用户没给就停下来问，不用历史值臆测；
- 不把主口令作为 git 提交信息、文件名、注释、issue/文档内容。

最小范式（主口令来自交互/环境，目标 token 不回显）：

```bash
# ENC_PASS 由用户当次提供；解出的 PAT 直接管道给 gh，不在屏幕/文件留明文
ENC_PASS="${ENC_PASS:?需要用户当次提供主口令}" \
  secrets decrypt "$HOME/.doubao/secrets/github_pat.enc" | gh auth login --with-token
```

## 四、二段因子（2FA/TOTP）：用 Microsoft Authenticator 配合

- 用户的二段因子统一由手机上的 **Microsoft Authenticator** 提供动态 6 位码（TOTP）。
- 当登录/操作触发 2FA 时：**请用户当下打开 Authenticator 读对应账号的 6 位码并提供**，agent 用它完成当次验证；验证码几十秒失效、用后即弃，不记录、不存储。
- agent **默认不持有 TOTP 共享密钥**、不自行代生成验证码；只有当某服务的 TOTP secret 已按规范加密存于本机 `.enc` 且用户明确授权自动生成时，才可走解密自动取（属于开发者凭证范畴，按第三节处理）。
- 给账户开 2FA 时产生的**恢复码**：如用户需要留存，按开发者凭证一样加密存 `.enc`（不放明文、不进公开仓）。
- 注：Microsoft Authenticator 的"密码自动填充"已停用，它在此体系里只承担 TOTP/passkey，不当密码库。

## 五、非交互无人值守：master.pass（用户知情才启用）

流水线无法交互、又必须自动解密时，才使用本机主密码文件——这是"自动化可用"与"不把主口令写进仓库"之间的标准折中：

- 固定路径 `~/.doubao/secrets/master.pass`（一行，`chmod 600`，目录 700，**在所有仓库之外、永不入库**）；
- 脚本三级回退：已 export 的 `ENC_PASS` > `master.pass` > 交互输入，全缺则报错退出（参考实现属 mac-system-toolkit 加解密能力）；
- 建立方式：`umask 077; printf '%s' '<主口令>' > ~/.doubao/secrets/master.pass && chmod 600 ~/.doubao/secrets/master.pass`，由用户本人或经用户当次授权建立；
- 它是本机当前用户可读的明文文件（主口令无法再加密自身），因此**仅限可信本机**，不进 git、不进云盘同步目录、不跨机明文拷贝；新机器线下重建。
- 是否启用由用户决定；用户没要求无人值守时，默认走第三节的交互方式，不主动创建 master.pass。

## 六、红线清单

- [ ] 不在任何仓库/脚本/文档/commit/聊天/截图/日志里出现真实主口令；公开仓示例只用 `<主口令>`。
- [ ] 不猜、不写死、不复用历史主口令；需要就交互问用户。
- [ ] 解密结果不在对话回显、不写入会被提交或同步的文件，用完 `unset`。
- [ ] 不替用户决定更换密码、不主动装个人密码管理器；用户主动提出加强再给方案。
- [ ] 2FA 动态码当次向用户要、用后即弃，不擅自长期保存。
- [ ] `master.pass` 必须 600、仓库外、不入库、不入云同步。

## 七、来源与延伸

- 主口令来源优先级与 `master.pass` 折中由 mac-system-toolkit 的加解密能力提供（本文不复制）。
- AI/agent 不应持久持有用户秘密、用后即弃：见 [ai-agent-credentials.md](ai-agent-credentials.md) 及其来源。
- 仅当用户主动想加强个人账户时再参考：NIST SP 800-63B https://pages.nist.gov/800-63-4/sp800-63b.html 、EFF Diceware https://www.eff.org/dice ；Microsoft Authenticator 能力边界 https://support.microsoft.com/en-US/authenticator/changes-to-microsoft-authenticator-autofill
